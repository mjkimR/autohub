# [PROP-updated-at-maintenance] Maintain updated_at on every owner write

## 1. Background & Hypothesis

`SPEC-owed-item-contract` found that `updated_at` does not advance on ordinary writes
(`FB-timestamp-updated-at-never-maintained`). Every Hub model inherits it from `TimestampMixin` in the pinned
`app-layer-base` package (`modules/hub/pyproject.toml`, app-common revision `2837f847`):
`updated_at` has `server_default=func.now()` and `server_onupdate=func.now()`. `server_onupdate` only marks the column
as generated by the database; SQLAlchemy emits nothing for it, and no migration creates an update trigger
(`modules/hub/migrations/versions/20260921_215029_574ca96e6e8e_init.py` declares only `server_default=now()`). No
`before_update` listener or `onupdate` exists in `modules/hub/app`. An ORM update therefore leaves `updated_at` at the
insert time.

Only three write paths set it by hand:

- `modules/hub/app/features/execution/flows/repos.py` (flow revision and release activation);
- `modules/hub/app/features/project_management/pipeline_runs/repos.py` lease release (`updated_at=now`), which the
  scheduler reaches after each advancement step (`pipeline_runs/usecases/advancement.py`); and
- `modules/hub/app/features/project_management/connection_tests/repos.py` `finish_step`.

Operator and webhook transitions of a PR run (`pipeline_runs/usecases/control.py`, `transitions.py`,
`interactions.py`), and every write to the other models, do not set it.

### Affected models

All 47 models in 18 files inherit `TimestampMixin`. The ones whose `updated_at` is read as a last-write or state-entry
time:

| Model (file under `modules/hub/app/features/`) | Reader that assumes a last write | Effect today |
| --- | --- | --- |
| `PipelineRun` (`project_management/pipeline_runs/models.py`) | `owed_items/repos.py` `stopped-run` and `failed-run` `waiting_since`; `pipeline_runs/usecases/queries.py` `list_attempts` (`finished_at` of a final run); `execution/tasks/domains/maintenance/history.py` `delete_runs` (30-day retention age); `pipeline_runs/repos.py` `list_unannounced_stops` (`updated_at > since`) and observation ordering; `mark_stop_announced` comment "its last update stays the moment its state last changed"; `RunHeader.svelte` "Updated" | Partly maintained: correct after a scheduler lease release, stale after an operator pause, cancel or resume or a webhook transition. A run canceled by an operator long after creation reports a wrong finish time, and its retention age counts from its last lease release or creation, so it can become eligible for deletion early. |
| `WorkPlan` (`project_management/work_plans/models.py`) | `owed_items/repos.py` `work-plan-proposed` `waiting_since` | Waiting time is the creation time. |
| `WorkItem` (`project_management/work_plans/models.py`) | `owed_items/repos.py` `work-item-attention` `waiting_since`; `CAP-WORK-work-plan-execution` retention ("its own last update") through the attached run | Waiting time is the creation time. |
| `ReplacementLink` (`project_management/work_plans/replacement_models.py`) | `owed_items/repos.py` `work-item-replacement` `waiting_since` | Waiting time is the creation time. |
| `SddBatch` (`project_management/sdd/batch_models.py`) | `owed_items/repos.py` `sdd-batch-attention` `waiting_since` | Waiting time is the creation time. |
| `ConnectionTest` (`project_management/connection_tests/models.py`) | `owed_items/repos.py` cleanup fallback; `maintenance/repos.py` `pending_tests` ordering | Maintained by `finish_step`; other writes leave it. |
| `ScheduleConfig`, `ScheduleJob`, `Connector`, `SystemConfig` (`scheduling/`, `configuration/`) | `updated_at` sort aliases in each `query_options.py`; `SystemConfigsView.svelte` "Updated" | Sorting by `updated_at` equals sorting by creation. |

`NotificationChannel` (`notifications/usecases.py`) and `WorkPlanTemplate` (`work_plans/template_service.py`) return
`updated_at` in their reads, and every `TimestampSchemaMixin` read exposes it, so API clients see the creation time
labeled as an update time.

The contracts that rely on it: `CAP-PR-owed-items` (`waiting_since` "otherwise the owner row's `updated_at`"),
`CAP-EXEC-scheduling-maintenance` ("A terminal run's age uses `updated_at`") and `CAP-WORK-work-plan-execution` ("its
own last update"). Tests pass because fixtures set `updated_at` explicitly
(`tests/integration/features/execution/maintenance/test_retention.py`).

Hypothesis: maintaining `updated_at` on every ORM and Core update makes these contracts true without changing them.

## Source feedback

- `FB-timestamp-updated-at-never-maintained`: received in full. Its Evidence line "only flows/repos.py sets it
  explicitly" is incomplete; the survey above adds the lease release and connection-test step writers.

## 2. Technical Spike Questions

- **Q1 (mechanism and ownership)**: Is the fix an ORM `onupdate` on a Hub-owned mixin or event listener, a database
  trigger per table, or a change to `TimestampMixin` in app-common (an upstream change Hub adopts by moving its pin)?
  The app-common skill and `devkit rules check` architecture rules apply to the first option. SQLite tests must keep
  working with the chosen mechanism.
- **Q2 (Core updates)**: ORM `onupdate` does not cover `update()` statements that list explicit values. Which Core
  updates (`pipeline_runs/repos.py`, `connection_tests/repos.py`, `flows/repos.py` and others found by search) need
  `updated_at` added, and which must keep it unchanged, like `mark_stop_announced`, which writes
  `updated_at=PipelineRun.updated_at` on purpose?
- **Q3 (bookkeeping writes)**: Which writes are bookkeeping and must not count as a change (lease renewals,
  notification marks, observation cursors)? Would advancing `updated_at` on them make owed waiting times reset on
  every scheduler tick, so that `waiting_since` needs a state-entry time instead?
- **Q4 (existing rows)**: Do existing rows keep their creation-time values, or does a migration backfill a better
  estimate where one exists (for example a final run's last attempt `finished_at`)?

## 3. Proposed Design & Impact

Direction, to be settled in Planning: every write that changes a Hub-owned row advances `updated_at`, through one
mechanism chosen in Q1, with explicit exceptions for the bookkeeping writes Q3 names. A regression test per affected
reader updates a row through its real write path, without setting `updated_at` in the fixture, and asserts the
reader's result: owed `waiting_since` per kind, run `finished_at`, retention eligibility and unannounced-stop
selection.

Expected impact: the shared model base or migrations, the listed Core update statements, their tests, and wording in
`CAP-PR-owed-items`, `CAP-EXEC-scheduling-maintenance` and `CAP-WORK-work-plan-execution` only where a bookkeeping
exception or a state-entry time changes what they state. If Q3 shows that `waiting_since` needs dedicated state-entry
columns, that is a contract change and goes to a separate feature proposal.

Non-goals:

1. Adding state-entry timestamps to owner models.
2. Changing retention windows, owed-item kinds or their order.
3. hub-ui changes; the screens already display `updated_at` as an update time.
